# Entorno de trabajo: control de versiones y contenedores.

## Control de versiones, Git y GitHUb.
El **control de versiones** es un software que registra los cambios realización en el código a medida que se edita y guarda esos cambios para su recuperación de requerirse, esto lo hace de una forma segura, eficiente y ágil a lo largo del tiempo.

Cuando el usuario edita código, el sistema de control de versiones toma una “foto” de los archivos, la guarda permanentemente para ser accesible en un futuro. Debido a que las demandas de un usuario aumentan, el control de versiones ayuda a los equipos a trabajar juntos y entregar en tiempo. Resuelve problemas de colaboración y organización, distribuyendo soluciones, evitando producción de errores de quienes retoman el trabajo, unificando el flujo de versiones que con ayuda de la sincronización de versiones permite hacer cambios sin que se solapen. Además de todo lo anterior todas las modificaciones se guardan en un historial, un registro que resulta útil par revisar las etapas del proyecto, corregirlo o recuperarlo fácilmente.

De este modo nos podemos encontrar con **Git** una herramienta de código abierto. Este software se instala de forma local y su función principal resulta en gestionar las versiones del proyecto de forma local y distribuida. Git es completamente independiente de cualquier otra plataforma externa, lo que implica que se puede utilizar sin necesidad de terceros.

Por otro lado, **GitHub** es una plataforma que trabaja en la nube para alojar repositorios de Git, este servicio aloja de forma remota los proyectos trabajados con Git, volviéndolo accesible desde cualquier lugar. De este modo GitHub añade capas de colaboración, automatización y gestión de proyectos, llevando el entorno colaborativo a otro nivel.

En este sentido un **commit** funciona como tomar la “fotografía” del proyecto guardando el estado en un momento preciso, añade una nota explicativa que ayuda con la revisión de avances, por ejemplo, cuando se crea un archivo de texto para adjuntar alguna investigación y se hace un commit se ejecuta con el mensaje descriptivo “Agregar Investigación sobre caso de estudio” o algo relacionado con la modificación, archivo, o acción.

En este caso una **branch** es una línea de trabajo independiente a la principal, que al ser creada te permite trabajar una “copia” del proyecto con modificaciones propias sin afectar lo ya estipulado o trabajado en la principal, por ejemplo, si necesitáramos probar líneas de código nuevas pero se da el caso de modificar otras en otro archivo que ya estaba creado, se puede trabajar dentro de esta nueva rama, hacer las modificaciones necesarias, corroborar que funciona perfectamente y posterior a eso enviar los cambios a la rama principal.

Estos cambios de una rama secundaria a la principal se llevan a cabo mediante un **merge** que integra el trabajo que se realizo por separado de vuelta a la línea principal, por ejemplo, si dos integrantes están trabajando en asuntos diferentes, no necesitan estar de acuerdo para subir sus cambios, se trabaja en ramas separadas y se fusionan al terminar cada uno a su tiempo. Pero también existe la posibilidad de un **merge conflict** que ocurre cuando dos personas modifican la misma línea de un mismo archivo de manera diferente en distintas ramas, impidiendo la fusión y solicitando al equipo que decida que versión es la que se fusionara, por ejemplo, si en la rama principal se modifica la línea 90 de un archivo principal, y al mismo tiempo alguien mas modifica esta misma línea, al momento de querer fusionar las ramas Git genera un conflicto para que se decida que versión se conserva antes de la fusión.

Y para poder revisar estos cambios antes de fusionarlos, se ejecuta un **pull request** que permite proponer los cambios en el repositorio, solicitar la fusión con alguna rama especifica. En esta solicitud de GitHub, se adjunta la descripción de los cambios, configuraciones o alteraciones para que alguien con los permisos necesarios lo revise y termine de fusionar.

Dentro de todo lo que un usuario puede llegar a subir hay archivos basura, que se generan cuando ejecutas algún programa, archivos que dejan de ser necesario o que se crean solo para el uso loca, todos estos archivos se pueden evitar subir al repositorio con un archivo **.gitignore** que en su contenido da instrucciones a Git sobre que archivos o carpetas debe ignorar por completo cuando alguien suba sus avances al repositorio, por ejemplo, al ejecutar varias pruebas de algún programa, o generar archivos con datos de prueba y demás, no queremos que esos archivos queden dentro del repositorio, por lo que se agrega la extensión de esos archivos o el nombre de la carpeta al archivo .gitignore para que evite subir estos archivos por accidente.

Adicional a esto el archivo **README.md** es la explicación oficial del proyecto, donde se debe de colocar todo lo necesario para que alguien externo pueda comprender lo que se trabajó el proyecto, como hacer funcionar la aplicación en su computador, en general resulta en un manual para el usuario.

## Contenedores y máquinas virtuales.
Un **contenedor** es un paquete de un software, ejecutable de forma independiente que incluye todo lo necesario para ejecutar una aplicación, un contenedor aísla una aplicación en una zona donde no puede ser alterada por alguna función o aplicación externa a ese contenedor. Que en la practica resulta ser una mejor opción a comparación de maquinas virtuales por tres grandes diferencias:
- **El arranque.** Un contenedor tiene la capacidad de arrancar en milisegundos, porque no necesita cargar un sistema operativo, solamente ejecuta un proceso en las condiciones del anfitrión. Mientras que las VMs tardan minutos por tener que cargar el sistema operativo invitado completamente desde cero.
- **El tamaño.** Los contenedores suelen pesar MB, esto por que solo empaquetan la aplicación y las dependencias de esta. Las MVs necesitan GB porque incluyen su propio sistema operativo.
- **El aislamiento.** Los contenedores ofrecen un aislamiento a nivel de sistema operativo. Las MVs aíslan a nivel de hardware, proporcionando un límite de seguridad aún más estricto, pero consumiendo muchísimo mas recursos.
En el contexto de los contenedores, una **imagen** es la plantilla que contiene las instrucciones, el código, dependencias y configuración estándar para construir un contenedor. Un **contenedor** es la instancia ejecutable y en vivo de una imagen. El volumen de un contenedor es el mecanismo de almacenamiento persistente, permitiendo que los datos generados por el contenedor sobrevivan después de la eliminación o reinicio de un contenedor, almacenándolos directamente en el sistema. Y un **puerto publicado** es un puerto de rede de la maquina anfitriona que se mapea hacia un puerto interno del contendor, permitiendo que se pueda acceder a los servicios que se ejecutan dentro del contenedor

## Entorno virtual de Python.
Un entorno virtual es un árbol de directorios autónomo, que aísla todas las instalaciones de paquetes y herramientas para un proyecto específico, separándolas de los paquetes instalados a nivel global en el sistema operativo. No modifica la versión por que la herramienta de entornos virtuales no compila, reinstala ni altera el ejecutable principal de Python, esto lo evita creando symlinks o copias del binario de Python hacia el directorio del entorno local. El entorno redirige la instalación de paquetes hacia uno propio que garantiza que el sistema base no sea modificado.

Unas de las razones por las que se utilizan versiones fijas de Python es por la **reproducibilidad y prevención de fallos**, al utilizar éticas como “latest” en la construcción de imágenes para contenedores funciona como un puntero hacia la versión mas reciente, si se construye una aplicación hoy, y en seis meses se actualiza, el código podría corromperse debido a cambios incompatibles o dependencias obsoletas que sin aviso previo fueron modificadas. Otra razón más es **la optimización y seguridad**, las etiquetas como “-slim” proporcionan una imagen sin paquetes y compiladores que no son necesarios para correr la aplicación, reduciendo drásticamente el peso de la imagen y la zona de ataque ante vulnerabilidades.
